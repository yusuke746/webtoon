# AI漫画スタジオ（連載・拡張版）

あらすじを入力 → ストーリー構成 → キャラ生成 → 作画 → コマ割り・セリフ配置 → 出力 までを自動化する連載対応の漫画制作Webアプリ。

## 差別化ポイント（独自拡張）

| # | 機能                         | 実装                                                                                                                                                                                 |
| - | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1 | **伏線回収エンジン**   | 伏線を「導入話数 / 回収予定話数 / 状態 / 関連キャラ・アイテム」を持つ構造データとして管理。回収予定を過ぎた未回収伏線を自動検出して警告（`apps/server/src/engines/foreshadow.ts`） |
| 2 | **カスタマイズ自由度** | 画風・コマ割りルール・構成テンプレートを作品ごとに上書き可能。全生成ステップに「手動編集 → 再生成」ループあり                                                                       |
| 3 | **AI同士の議論機能**   | 編集者 / プロット担当 / 読者代表の3役の Claude が議題を議論し合意案を生成。ログ保存・ユーザー介入・採否選択・構成への自動反映に対応（`apps/server/src/engines/discussion.ts`）     |
| 4 | **データの使い回し**   | キャラ・世界観・画風を「ライブラリアセット」として保存し、別作品へキャスティング可能                                                                                                 |
| 5 | **みやすいUI/UX**      | 制作フローを「エピソード選択 → シーン構成 → ネーム生成 → 作画」のステッパーで可視化し、その順に画面遷移する。長時間処理は非同期ジョブ化して進捗を表示                             |
| 6 | **一貫性アセット工房** | キャラ・背景の参照画像を Replicate で複数枚生成して1枚を採用。さらに対象専用の LoRA を Replicate の trainings API で学習できる                                                       |

## 書庫（連載アーカイブ）と連載マネージャー

作品ごとに **人間が読める Markdown のフォルダ** を保ち、生成のたびに書き出す。
「連載マネージャー」はこのフォルダを根拠に各話の要約と「連載メモ」（人物の現在地・確定設定・未回収の伏線）を
Claude で更新し、以降の構成生成・ネーム生成のプロンプトへ文脈として渡す。
LoRA が «絵» の一貫性を担うのに対し、書庫は «物語» の一貫性を担う。

```
data/series/<id>-<作品名>/
  bible.md             シリーズバイブル。auto ブロックは設定から再生成、連載メモはマネージャー、作者メモは自由記述
  characters/*.md      キャラ設定（参照画像のコピー付き）
  episodes/NN/script.md    構成 + ネーム（DB から毎回書き出し）
  episodes/NN/summary.md   話の要約（マネージャー生成。手直し可）
  episodes/NN/images/      作画済みコマ
  foreshadow.md        伏線の状態
  meetings/*.md        AI編集会議のログ
```

- ネーム生成が終わると自動で「書庫へ登録」（要約生成 → 連載メモ更新）される（`ARCHIVE_AUTO_REGISTER=0` で無効）。作画が終わった時点で要約がなければそこでも登録する
- Claude CLI は作品フォルダを作業ディレクトリにして起動し、読み取りツール（Read/Glob/Grep）だけ許可される。
  プロンプトに載せきれない過去話の脚本を Claude 自身が確認できる（`SERIES_FILE_ACCESS=0` で無効）
- UI の「書庫」画面で bible.md / summary.md を直接編集でき、次の生成から反映される
- `data/series/` は .gitignore 済み。アーカイブ自体を Git 管理したい場合は `SERIES_DIR` を別リポジトリのフォルダに向ける

## UI: RPG 風オフィス（編集部ビル）= 制作工程そのもの

画面はドット絵の「編集部ビル」。プレイヤーは **担当編集** で、NPC に仕事を頼むことで漫画が進む。

1. 2F の脚本家に「構成を書いてもらう」→ 脚本家は机へ向かい「作業中…」（ジョブ）
2. 終わると頭上に「!」。話しかけると新しい話の構成を窓の中で受け取り、「この話から進める」を選ぶ
3. 「シーン構成を見せて」で確認し、「OK、3Fの漫画家に回す」か「直してほしい（指示を書く）」
4. 3F の漫画家に「ネームを切ってもらう」→ 原稿（ページプレビュー）を受け取り「OK、作画に入ってくれ」か「ネームを直してほしい」
5. 作画が終わると「次の話へ」。書庫番がその話を自動で書庫に登録する（要約・連載メモ更新）
6. 右の **進行表** に話ごとの「構成 / ネーム / 作画 / 書庫」と次にやることが出る

構成ができたら、ネームの前に **設定画** を作る（キャラクターデザインの工程）。
2F の設定担当に「設定画のない N 人の設定画を作ってもらう」と頼むと、キャラごとに候補を数枚描き、
設定担当（Claude）が候補を見比べて設定に最も近い1枚を選んで持ってくる。編集は「おすすめを採用」か「別の候補を見る」。
採用すると、その1枚から **正面・横顔・全身・表情** の4枚セットを派生させ（`DESIGN_VIEWS=0` で無効）、作画の参照と作画チェックの比較対象にする。
設定画がないキャラが出る話で作画に入ろうとすると、漫画家が「先に設定画を」と言う（設定画なしで描くことも選べる）。

背景も同じ流れ。2F のロケハン担当に「構成とネームから場所を拾い出してもらう」と、繰り返し出てくる場所を背景として登録する。
続けて「設定画のない N 件の背景の設定画を作ってもらう」→ 候補を見比べておすすめ → 採用で **引き・入口から・細部・夜** の4枚セットを派生。
API: `POST /api/projects/:id/jobs/design {kind}`, `GET /api/projects/:id/design?kind=`, `POST /api/design/adopt`, `POST /api/projects/:id/jobs/locations`

**ロケハン写真の持ち込み**: 自分で撮った写真をロケハン担当に渡す（「ロケハン写真を渡す」／背景の一覧の「ロケハン写真を追加」）と、
その場所の候補は **写真の構図・建物の配置を保ったまま画風に合わせて起こす**（`stylizePhotoPrompt`。写真は `role='photo'` の参照画像として保管され、候補の見比べでも参照される）。
起こすモデルは画風のモデルが画像入力に対応していればそれ、対応していなければ `flux-kontext-pro`（`REPLICATE_STYLIZE_MODEL` で指定可）。
※ Google ストリートビューなど他サービスの画像を生成の入力に使うのは規約違反になるので、入力は自分で撮影した写真に限る。
API: `POST /api/uploads {dataUrl,name}`, `POST /api/backgrounds/:id/photos {urls}`

修正指示は自然言語で、サーバーの `jobs/revise-scenes`（シーン構成の書き直し）と `jobs/panels`（指示付きのネーム改稿）へ渡る。
従来のページは「書類で見る」から開ける補助に下げた（URL は従来のまま）。

| 階 | 部屋 | NPC → 開くページ |
| -- | ---- | ---------------- |
| 4F | 会議室 | 司会に議題を出すと、編集者・プロット担当・読者代表が **その場で議論する場面** になる（議事録は従来ページ） |
| 3F | 作画室 | 漫画家 → ネーム・作画（直近に開いた話） / 画材担当 → 画風・カスタマイズ |
| 2F | 脚本室・資料室 | 脚本家 → 制作フロー（エピソード選択・シーン構成） / 設定担当 → キャラクター / ロケハン担当 → 背景 |
| 1F | 編集部 | 受付 → 作品一覧（担当作品の選択） / 編集長 → ダッシュボード |
| B1 | 書庫 | 連載マネージャー → 書庫（連載アーカイブ） / 伏線ボード → 伏線 / アセット倉庫 → ライブラリ |

- 矢印キー/WASD で移動、Enter/Space で会話、クリックで歩いて話しかける。階段に乗ると上下階へ
- NPC に話しかけると会話ウィンドウが開く。まず作品の状態に応じた定型文（進み具合・未回収の伏線など）、
  次にメニュー（部屋に入る / 相談する・要望を伝える / また今度）
- 「相談する」はテキスト入力。NPC の役割（編集長・脚本家・漫画家・書庫番…）で Claude が答え、
  構成を変える要望なら「その内容を構成に反映する」が出る（既存の `apply-change` を呼ぶ）。API: `POST /api/projects/:id/talk`
- 相談・提案のとき NPC が知っているもの: あらすじ・全話の要約・伏線に加えて、**人物の外見と性格・登録済みの場所・担当中の話のシーン構成とネーム本文**、
  それに書庫の連載メモと各話の要約（書庫フォルダがあれば Claude がファイルを直接読むこともできる）。
- **縦読み（Webtoon）リーダー**: 作画済み（ネーム済みでも可）の話を全画面の縦スクロールで読む。3F の漫画家に「縦読みで読む」、
  または作画・ネームのページの「縦読みで読む」から `/projects/:p/episodes/:e/read` を開く。
  読み方向が「縦スクロール」の作品はそのまま 1 列、ページ割りの作品もコマを読み順（rtl は同じ段で右→左）に並べ直して縦に流す。
  コマの高さはネームのレイアウト比から決め、作画のアスペクト比も同じ計算で生成している。「ページ」に切り替えればページ単位でも読める。
  Space/↓ で 1 画面進む、Esc で戻る。話末に前後の話へのリンク。読んだ位置は話ごとに覚える。
  読み方向を「縦スクロール」にすると、ネーム生成は x=0・w=列数 固定で h だけで長さを決める縦 1 列になり、セリフは上から順に置く。
- **4F の会議は部屋の中の場面**: 司会に「議題を出して会議を開く」と、テーブルを囲む編集者・プロット担当・読者代表が
  順に発言し、発言者の頭上に吹き出しが出る。発言は 1 つずつ Enter で読み進め、まとめ役の合意案まで来たら司会が提案を読み上げ、
  その場で「採用して構成に反映」「採用のみ」「意見を言ってもう一度議論」「不採用」「後で決める」を選ぶ。
  途中で Esc で席を外しても議論は続き、終わると司会が「!」で知らせる（「結論を聞く」「最初から見る」）。
  議論の各発言にも、相談と同じ作品の中身（人物・場所・各話のシーン構成とネーム）と書庫の連載メモが渡る。
  採否を決めると結論は書庫の `bible.md`「会議の決定事項」ブロックに残り（採用は決定した変更まで、不採用は要約だけ）、
  採用なら連載メモにも織り込まれる。決定事項は以後の構成・ネーム生成と相談・提案の文脈にも「従うべき方針」として渡る。
- **提案**: 編集長・脚本家に「次の展開を提案してもらう」「気になる点を聞く」、進行担当に「伏線の回収案を聞く」。
  役割の観点で 3 案（見出し・内容・反映用の指示文）が返り、編集長・脚本家・進行担当の案は「案Nを構成に反映する」でそのまま構成へ反映できる。
  API: `POST /api/projects/:id/propose {npcId, mode: 'next'|'review', episodeId?}`
- 作業中のジョブは NPC の頭上に「作業中…」と出る
- ドット絵は 16×24 の人物（3方向×歩行2フレーム、髪型・服色・眼鏡をレイヤー合成）と陰影付き 16×16 タイル。
  `apps/web/src/office/art/` に文字列で定義しており、差し替えや追加はそこを編集する
- ヘッダの「クラシック表示」で従来のサイドバー UI に切り替えられる（`localStorage` の `ui:classic`）
- 実装は `apps/web/src/office/`（`art/` ドット絵 / `sprites.ts` 描画 / `floors.ts` フロア定義 / `OfficeMap.tsx` / `TalkWindow.tsx` 会話 / `dialogue.ts` 定型文 / `OfficeLayout.tsx`）

## 制作フロー

```
ダッシュボード（準備状況の可視化）
   ↓
[1] エピソード選択  /projects/:id/episodes
   ↓
[2] シーン構成      /projects/:id/episodes/:eid/scenes    … 話の流れを確認・編集
   ↓
[3] ネーム生成      /projects/:id/episodes/:eid/panels    … コマ割り・セリフ・背景割り当て
   ↓
[4] 作画            /projects/:id/episodes/:eid/art       … コマ単位 / 一括（非同期ジョブ）
```

各画面の上部にステッパーが常駐し、現在地と到達可否（例: ネーム未生成なら作画は無効）が分かる。

## 絵の一貫性（LoRA なし）: 固定文 + 参照画像 + 作画チェック

画像は Replicate のモデルが描き、Claude は «指示を書く» と «出来た絵を見て判定する» を担う。

| 手段 | 内容 |
| ---- | ---- |
| **絵の固定文** | キャラ・背景ごとに Claude が一度だけ英語の外見タグ列（`visualPrompt`）を作り、以後すべてのコマで同じ文言を画像プロンプトの先頭に置く |
| **設定画（参照画像）** | 設定担当が候補を描いて Claude が選び、採用した1枚と派生の4枚セット（正面・横顔・全身・表情 / 背景は引き・入口・細部・夜）を **マルチリファレンス対応モデルに画像として渡す**。コマに出るキャラと背景のシートを配列で渡し、プロンプト先頭に「[image 1] = 主人公 (character sheet)…」と対応を書く |
| **文字を描かせない** | プロンプトに「no text / no speech bubbles」を常に付け、SD 系モデルには negative prompt も渡す。吹き出しはアプリが描くので、画像に変な文字が混ざらない |
| **作画チェック** | 生成されたコマを Claude が Read で開き、設定・参照画像と照合（髪色・服・人数・文字の混入・破綻）。不一致なら修正ヒント付きで描き直す（`ART_CHECK_MAX_RETRY`、既定2回）。それでも駄目なら「要確認」として指摘を残し、編集が「描き直す」を選べる |

`ART_CHECK=0` でチェックを止められる。LoRA 学習はコードとして残っているが、画面からは外した（コストが高く小規模学習では崩れやすいため）。

### 作画モデルの選び方（参照画像をどう受け取るか）

モデルごとに参照画像の入力名と枚数が違うため、`apps/server/src/image/models.ts` の台帳で吸収する。画風設定の画面と 3F 画材担当が、いまのモデルが設定画を渡せるかを教えてくれる。

| モデル | 参照画像 | 備考 |
| ------ | -------- | ---- |
| `google/nano-banana`（Gemini 2.5 Flash Image） | 複数（最大10） | **既定のおすすめ**。キャラ・背景のシートを同時に渡せる |
| `bytedance/seedream-4` | 複数（最大10） | 高解像度 |
| `openai/gpt-image-1` | 複数 | `extraInput` に `openai_api_key` が必要 |
| `black-forest-labs/flux-kontext-max` | 1枚 | 主役の顔だけ。設定画セットの派生にも使用 |
| `black-forest-labs/flux-dev` | 1枚（img2img） | 同一性は保てない |
| `black-forest-labs/flux-schnell` | なし | 設定画を渡せない。下書き用 |

台帳にないモデルは `IMAGE_REF_INPUT=入力名[:枚数]` で参照画像の入力を指定できる。`IMAGE_ASPECT_INPUT=0` でアスペクト比の入力を止める（モデルが受け付けない場合）。
モデル名と入力仕様は変わるので、Replicate のモデルページで現行の入力名を確認すること。

## 一貫性アセット（キャラ・背景を毎回同じ絵で描く）

「参照画像URL」「LoRA URL」を手入力する欄しかなかった箇所に、生成手段を用意している。

| 手段               | 場所                                  | 内容                                                                               |
| ------------------ | ------------------------------------- | ---------------------------------------------------------------------------------- |
| **参照画像** | キャラクター / 背景 → ビジュアル工房 | 設定文 →（Claude）英語プロンプト → Replicate で候補を複数枚生成 → 1枚を「採用」 |
| **LoRA学習** | 同上 → LoRAタブ                      | 採用候補を ZIP 化 → Replicate files API へアップロード → trainings API で学習    |
| **背景**     | サイドバー「背景・ロケーション」      | 場所を登録すると、ネーム生成時にコマへ自動割り当て（名前一致）され作画へ渡る       |

採用した参照画像・学習した LoRA は、作画時に自動でパネルへ渡される。
背景（ロケーション）もキャラと同じく参照画像・LoRA の両方を持てる。

### 1コマに適用できる LoRA / 参照画像は1つずつ

flux 系モデルは `lora_weights` と `image` を1つずつしか受け取れないため、
`resolveConsistencyInputs()`（`src/image/ImageClient.ts`）が優先順位を一元的に決める。

```
登場キャラ  →  背景  →  画風
```

- 人物のいるコマ: 顔の一貫性を優先してキャラの LoRA / 参照画像が使われる
- 人物のいない情景コマ: 背景の LoRA / 参照画像が使われる
- 適用されなかった候補はサーバーログに警告として出る（「学習したのに効かない」を追跡できるように）

人物と背景の LoRA を同時に効かせたい場合は、画風設定で複数LoRA対応モデルを選び、
`ArtStyle.extraInput` にそのモデル固有の入力（例: `hf_loras`）を直接指定する。

### LoRA学習の前提（実費・時間がかかります）

- Replicate 上での実費（数ドル程度）と時間（20〜40分）が発生する
- 学習画像は10枚以上を推奨（参照画像タブでまとめて生成できる）
- `REPLICATE_LORA_TRAINER` に **version 付き** で学習モデルを指定する必要がある（`owner/name:versionId`）
- `REPLICATE_LORA_DESTINATION` の出力先モデルは **Replicate 上に事前作成** しておく必要がある

UI の「前提条件をチェック」で、上記のうち何が足りないかを開始前に確認できる。

### 生成エンジンの前提

- **テキスト生成**: Claude CLI（MAX契約）をサブプロセス実行し標準出力を受け取る。APIキー不要。
  `LLMClient` インターフェースでラップ済みのため、将来 API 直叩き等へ差し替え可能。
- **作画**: Replicate API（`REPLICATE_API_TOKEN`）。画風ごとにモデル / スタイルプロンプト / LoRA を設定でき、
  パネルごとに登場キャラの LoRA・参照画像が自動で渡される（一貫性維持）。

## 使い方（生成フロー）

1. **作品作成**: タイトルとあらすじを入力
2. **カスタマイズ**（任意）: コマ割りルール・構成テンプレート・画風を設定
3. **構成を生成**: 話数構成・シーン・伏線が自動生成され、伏線ボードに登録される
4. **キャラクターを生成**: 外見・性格の設定を生成（手動編集可。参照画像 / LoRA を紐付け可能）
5. **各話でネームを生成**: コマ割り・セリフ・画像プロンプトを生成。生成後に「ネーム演出担当」「読者代表」のAIが自動で批評→改稿するループが走り（回数はカスタマイズで0〜2回に変更可）、批評ログは AI編集会議に保存される。セリフには吹き出し位置（右上/左下など）が付与され、ビューアで重ならずに描画される（コマ単位で手動編集可）
6. **作画**: コマ単位 or 一括で Replicate により画像生成。ページプレビューでコマ割り+フキダシを確認
7. **連載を続ける**: 「構成を生成」で続きの話数を追加。伏線の回収漏れは自動警告
8. **迷ったら AI編集会議**: 議題を投げて3役の Claude に議論させ、合意案を採用 → 構成へ自動反映

### 非同期ジョブ

数十秒〜数十分かかる処理（AI議論・一括作画・参照画像生成・LoRA学習）はジョブ化され、
HTTP は即座に `Job` を返す。進捗は `jobs` テーブルに保存されるためリロードしても追跡できる。
実行自体はプロセス内メモリのため、サーバー再起動時に残った実行中ジョブは起動時に失敗扱いへ倒す。
